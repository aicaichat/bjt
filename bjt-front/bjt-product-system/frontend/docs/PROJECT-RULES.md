# BJT产品管理系统 - 开发规则

## 核心原则

1. **1:1复刻原则**: 每个页面必须与mockup保持完全一致，包括样式、布局和交互
2. **正确命名原则**: 组件名称、目录和路由必须反映页面的实际功能
3. **单页单任务原则**: 每次只修改一个页面，完成后立即提交
4. **明确对应原则**: 每个React组件必须明确对应一个mockup模板
5. **真实数据原则**: 所有页面必须通过WordPress API获取真实数据，避免硬编码和模拟数据

## 标准页面复刻方法

### 1. 页面复刻定义

在BJT项目中，"页面复刻"明确定义为**直接基于现有mockup代码进行改造**，而非重新实现功能或重构设计。复刻的目标是创建与mockup在视觉和行为上完全一致的React实现。

### 2. 复刻流程步骤

1. **分析原始HTML页面**
   - 全面分析mockup中的HTML结构
   - 提取所有CSS样式和响应式规则
   - 识别JavaScript交互逻辑
   - 记录外部依赖和资源

2. **HTML转React转换**
   - 将HTML结构直接转换为JSX
   - 替换HTML属性为React属性（如`class`→`className`）
   - 处理自闭合标签（如`<img>`→`<img />`）
   - 保持原始HTML的嵌套结构不变

3. **CSS处理原则**
   - 直接复制原始CSS样式
   - 保留所有原始CSS类名和前缀
   - 确保响应式设计规则完全匹配
   - 不进行CSS重构或优化

4. **JavaScript交互转换**
   - 将原始的JavaScript事件处理转换为React事件
   - 使用React状态管理代替DOM操作
   - 保持原始逻辑和执行流程不变
   - 函数命名尽量与原始代码保持一致

5. **WordPress API集成**
   - 识别页面需要的动态数据
   - 使用WordPress REST API端点替换静态数据
   - 维护数据加载状态和错误处理
   - 保持与API数据结构的一致性

6. **100%视觉对比验证**
   - 使用视觉对比确保完全一致
   - 检查所有交互功能的行为匹配
   - 在不同分辨率下验证响应式行为
   - 验证真实API数据下的展示效果

### 3. 关键复刻准则

- **保持原始结构**: 即使有更"React化"的实现方式，也应遵循原始结构
- **不是改进，而是精确复刻**: 任何视觉或功能上的差异都是不可接受的
- **样式一致性**: 颜色、间距、字体、交互效果必须完全匹配
- **行为一致性**: 所有用户交互必须产生与原mockup相同的结果
- **动态数据适配**: 确保页面能正确显示来自WordPress API的真实数据

### 4. 数据处理与API集成

1. **禁止硬编码数据**
   - 所有产品信息、价格、库存等数据必须来自API
   - 禁止在代码中硬编码任何业务数据
   - 避免使用模拟(mock)数据，除非用于开发阶段临时测试

2. **WordPress API集成规范**
   - 使用统一的API服务模块处理所有请求
   - 采用适当的数据获取策略（React Query、SWR等）
   - 实现数据加载状态、错误处理和重试机制
   - 保持API请求逻辑与UI组件的分离

3. **数据映射与转换**
   - 创建适配器将API数据转换为组件所需格式
   - 处理API数据与UI展示之间的差异
   - 确保数据转换不改变原始页面的视觉呈现

4. **认证与会话管理**
   - 实现与WordPress认证系统的集成
   - 正确处理JWT或Cookie认证
   - 维护用户登录状态和权限控制

### 5. 常见复刻错误

- 重新设计组件结构而非复制原始结构
- 仅实现功能等效而忽视视觉细节
- 使用不同的CSS类名或选择器
- 简化或修改JavaScript交互逻辑
- 忽略细微的视觉细节或动画效果
- 硬编码业务数据而非使用API获取
- 使用不必要的模拟数据

## 文件与目录命名规则

1. **页面组件目录**: 使用与mockup文件名描述部分一致的PascalCase命名
   - 正确: `src/pages/Machines` (对应3-machines.html)
   - 正确: `src/pages/ShoppingCart` (对应6-shopcart.html)
   - 错误: `src/pages/Products` (用于购物车页面)

2. **mockup文件名参考**:
   - 始终参考最新的mockup文件名:
     - 1-index.html - 首页
     - 2-login.html - 登录页面
     - 3-machines.html - 设备选型页面
     - 4-option.html - 耗材选择页面
     - 5-spare.html - 备件选择页面
     - 6-shopcart.html - 购物车页面
     - 7-order.html - 订单确认页面
     - 8-po.html - 采购单页面
     - 9-orderlist.html - 订单列表页面

3. **主组件文件命名**:
   - 推荐: 使用功能描述性名称，如`ShoppingCartPage.tsx`
   - 避免: 过于通用的名称，如只用`index.tsx`

4. **API服务命名**:
   - 使用领域驱动命名，如`productService.ts`, `authService.ts`
   - 集中管理API端点和请求函数
   - 明确区分不同数据类型的服务

5. **CSS文件命名**:
   - 与组件同名，如`ShoppingCartPage.css`
   - 使用模块化CSS: `ShoppingCartPage.module.css`

6. **CSS类名前缀**:
   - 每个页面使用特定前缀，如`.cart-container`, `.machine-item`
   - 避免通用前缀，如仅用`.container`, `.item`

## 路由命名约定

1. **路由应反映页面功能**:
   - 购物车页面: `/cart` 或 `/shopping-cart`
   - 设备选型: `/machines`
   - 备件选择: `/spare-parts`

2. **嵌套路由应保持层次清晰**:
   - 备件选择: `/products/spare-parts`
   - 耗材选择: `/products/consumables`

## API集成开发流程

1. **API端点确认**:
   - 在开始页面开发前确认所需的WordPress API端点
   - 验证API返回数据结构与页面需求的匹配度
   - 记录API文档和使用示例

2. **数据获取策略**:
   - 确定使用React Query、SWR还是自定义hooks
   - 规划数据缓存和重新验证策略
   - 设计乐观更新和错误处理方案

3. **组件与API分离**:
   - 使用数据获取hooks隔离API调用逻辑
   - 确保UI组件专注于数据展示而非获取
   - 实现适当的加载状态和错误边界

4. **数据适配层**:
   - 创建转换函数将API数据映射到UI组件格式
   - 处理不同API版本或数据结构的变化
   - 确保数据处理不影响页面复刻的视觉一致性

## 开发流程规则

1. **开始新页面前**:
   - 查阅项目状态文档确认当前进展
   - 确认开发正确的页面及其对应mockup
   - 检查该页面的预定路径是否已被占用
   - 确认所需的WordPress API端点是否可用

2. **开发过程中**:
   - 使用正确的服务器端口(5174)
   - 定期保存工作
   - 保持对照mockup文件开发
   - 使用真实API数据测试功能

3. **完成页面后**:
   - 与mockup进行对比验证
   - 测试所有交互功能
   - 验证与WordPress API的集成
   - 更新项目状态文档
   - 提交代码，并添加清晰描述

## 问题处理流程

1. **发现页面丢失时**:
   - 记录在项目状态文档中
   - 检查可能的备份或历史版本
   - 计划重新实现

2. **发现命名或路径冲突**:
   - 记录在项目状态文档中
   - 创建迁移计划
   - 执行代码迁移和路由更新

3. **API集成问题**:
   - 记录具体的API错误和响应
   - 确认WordPress端点配置是否正确
   - 与后端团队沟通解决数据结构不匹配问题

3. **解决问题后**:
   ```
   # 更新问题状态
   - 将问题解决计划中的问题标记为已解决
   - 更新执行日志
   - 如果添加或修改了组件，更新页面对应关系表
   ```
