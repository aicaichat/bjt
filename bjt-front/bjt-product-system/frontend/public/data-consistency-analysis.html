🔍 BJT系统数据一致性问题深度分析

1. 根本原因分析

🔴 问题1：订单号管理混乱

原始设计缺陷：

  • 多处生成：Order页面、PO页面、OrderList页面都有自己的订单号生成逻辑
  • 格式不统一：有的用时间戳，有的用随机数，有的用数据库ID
  • 无唯一标识：没有全局唯一的业务订单号管理
// 🔴 问题代码示例 // Order页面 const orderId = `ORD-${Date.now()}-${Math.random().toString(36).substr(2, 6)}`; // PO页面 const generatePONumber = () => { const date = new Date(); return `PO-${date.getFullYear()}${(date.getMonth()+1).toString().padStart(2,'0')}${date.getDate().toString().padStart(2,'0')}-${Math.random().toString(36).substr(2, 6).toUpperCase()}`; }; // OrderList页面 const orderNumber = response.data.order_number || `ORDER-${Date.now()}`;

🔴 问题2：数据传递不完整

页面间数据丢失：

  • 只传递ID：页面跳转时只传递订单ID，不传递完整数据
  • 依赖API重取：每个页面都重新调用API获取数据，但API可能不一致
  • 状态不同步：前端状态变化没有及时反映到其他页面
// 🔴 问题代码示例 // PO页面确认后只传递基本信息 navigate('/orders', { state: { fromPO: true, poNumber: poNumber // 只传递订单号 } }); // OrderList页面需要重新获取数据 useEffect(() => { const fetchOrders = async () => { const response = await orderService.getOrders(); // 重新调用API setOrders(response.data); // 可能与PO页面数据不一致 }; fetchOrders(); }, []);

🔴 问题3：状态管理分散

缺乏统一状态管理：

  • 各自为政：每个页面维护自己的状态，没有全局状态
  • 数据孤岛：订单数据在不同页面有不同的格式和结构
  • 同步困难：一个页面的变化无法及时通知其他页面

2. 现在的解决方案

✅ 解决方案1：统一订单号管理

OrderNumberManager 统一管理：

  • 统一格式：PO-YYYYMMDDHHMM-XXXXXX
  • 唯一生成：全局只有一个订单号生成入口
  • 一致提取：统一的订单号提取和验证逻辑
// ✅ 解决方案代码 export class OrderNumberManager { // 统一生成订单号 static generateOrderNumber(): string { const now = new Date(); const dateTime = format(now, 'yyyyMMddHHmm'); const random = Math.random().toString(36).substr(2, 6).toUpperCase(); return `PO-${dateTime}-${random}`; } // 统一提取订单号 static extractFromOrderObject(order: any): OrderInfo { const orderNumber = order.orderNumber || order.order_number; return { id: order.id, displayNumber: orderNumber, isValid: this.validateOrderNumber(orderNumber) }; } // 统一验证 static validateOrderNumber(orderNumber: string): boolean { return /^PO-\d{12}-[A-Z0-9]{6}$/.test(orderNumber); } }

✅ 解决方案2：完整数据传递

页面间传递完整结构化数据：

  • 完整订单对象：传递包含所有信息的订单数据
  • 即时更新：接收页面立即更新本地状态
  • 数据验证：传递前验证数据完整性
// ✅ 解决方案代码 // PO页面确认时传递完整数据 const orderDataForList = { id: poNumber, orderNumber: poNumber, date: poDate, status: 'pending', total: summary.total, paymentMethod: paymentMethod, shippingInfo: { companyName: customerInfo.companyName, contactName: customerInfo.contactName, // ... 完整信息 }, items: products.map(product => ({ id: product.id, code: product.code, name: getProductName(product), // ... 完整商品信息 })) }; navigate('/orders', { state: { fromPO: true, poNumber: poNumber, confirmedOrderData: orderDataForList, // 传递完整数据 action: 'confirmed', timestamp: Date.now() }, replace: true });

✅ 解决方案3：统一状态管理

OrderContext 全局状态管理：

  • 全局状态：订单数据在全局Context中管理
  • 实时同步：状态变化自动同步到所有页面
  • 数据缓存：避免重复API调用
// ✅ 解决方案代码 // OrderList页面接收完整数据并更新状态 if (state.confirmedOrderData) { setOrders(prevOrders => { const existingOrderIndex = prevOrders.findIndex( order => order.orderNumber === state.confirmedOrderData.orderNumber ); const confirmedOrder = convertToUnifiedOrder(state.confirmedOrderData); if (existingOrderIndex >= 0) { // 更新现有订单 const updatedOrders = [...prevOrders]; updatedOrders[existingOrderIndex] = confirmedOrder; return updatedOrders; } else { // 添加新订单到列表顶部 return [confirmedOrder, ...prevOrders]; } }); }

4. 技术优势

✅ 现在的设计优势：

  • 单一数据源：OrderNumberManager 是订单号的唯一来源
  • 即时同步：页面间数据变化立即生效，无需重新加载
  • 类型安全：TypeScript 确保数据结构一致性
  • 可维护性：统一的数据管理逻辑，易于维护和扩展
  • 用户体验：无缝的页面跳转，数据始终保持一致
  • 错误处理：统一的数据验证和错误处理机制
