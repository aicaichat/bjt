# 二期需求代码提示词使用指南

## 📋 概述

本指南介绍如何使用生成的代码提示词来高效完成二期需求的开发任务。每个提示词都经过精心设计，旨在避免重复编写代码，同时确保不影响现有代码的稳定性。

## 📁 文件结构

```
output/coding-prompts/
├── overall_coding_prompts.md          # 总体提示词概览
├── coding_prompts_summary.json        # JSON格式的提示词总结
├── CODING_PROMPTS_USAGE_GUIDE.md      # 本使用指南
├── 一期测试未关闭问题_prompts.md      # 分类提示词文件
├── 销售试用反馈_prompts.md            # 分类提示词文件
├── 7-20讨论记录_prompts.md            # 分类提示词文件
├── P2_01_prompt.md                    # 单个需求提示词文件
├── P2_02_prompt.md                    # 单个需求提示词文件
└── ...                                # 其他需求提示词文件
```

## 🎯 使用流程

### 1. 了解项目概览
首先阅读 `overall_coding_prompts.md`，了解：
- 项目技术栈和开发原则
- 文件结构规范
- 开发流程和注意事项
- 所有需求的简要列表

### 2. 选择开发方式

#### 方式一：按分类开发
- 根据需求分类选择对应的提示词文件
- 适合按功能模块进行开发
- 文件：`一期测试未关闭问题_prompts.md`、`销售试用反馈_prompts.md`、`7-20讨论记录_prompts.md`

#### 方式二：按单个需求开发
- 直接选择具体需求的提示词文件
- 适合并行开发或特定需求开发
- 文件：`P2_XX_prompt.md`

### 3. 阅读提示词内容

每个提示词文件包含以下部分：

#### 需求描述
- 明确的需求说明
- 开发目标和预期效果

#### 开发目标
- 具体的开发任务列表
- 技术实现要点
- 代码修改指导

#### 实施说明
- 开发注意事项
- 风险提示
- 依赖关系说明

#### 建议代码结构
- 推荐的文件结构
- 前端、后端、数据库文件建议
- 测试文件建议

#### 测试指导
- 测试类型和范围
- 测试重点和注意事项

## 🔧 开发指导原则

### 1. 代码复用优先
- 优先使用现有的组件和工具
- 避免重复编写相似功能
- 利用现有的设计模式和架构

### 2. 渐进式开发
- 小步快跑，逐步完善
- 先实现核心功能，再优化细节
- 及时提交代码，避免大块修改

### 3. 向后兼容
- 确保新功能不影响现有系统
- 保持API接口的兼容性
- 谨慎修改核心组件

### 4. 测试驱动
- 编写充分的测试用例
- 确保功能稳定性和可靠性
- 进行回归测试

### 5. 文档完善
- 及时更新代码注释
- 维护技术文档
- 记录重要的设计决策

## 📝 提示词使用技巧

### 1. 理解需求背景
在开始编码前，仔细阅读需求描述，理解：
- 业务背景和用户需求
- 现有系统的相关功能
- 技术约束和限制

### 2. 分析现有代码
- 查找相关的现有组件和功能
- 了解数据流和状态管理
- 识别可复用的代码片段

### 3. 设计实现方案
- 根据提示词中的开发目标设计方案
- 考虑代码结构和文件组织
- 评估技术风险和复杂度

### 4. 逐步实现
- 按照提示词中的步骤逐步实现
- 及时测试和验证
- 根据实际情况调整方案

### 5. 代码审查
- 检查代码质量和规范
- 确保符合项目标准
- 验证功能完整性

## ⚠️ 注意事项

### 1. 避免重复开发
- 仔细检查现有代码库
- 使用现有的工具和库
- 避免重复造轮子

### 2. 保持代码质量
- 遵循项目代码规范
- 编写清晰的注释
- 确保代码可维护性

### 3. 测试充分
- 编写单元测试
- 进行集成测试
- 验证端到端功能

### 4. 文档更新
- 更新相关文档
- 记录API变更
- 维护开发日志

## 🎉 总结

通过使用这些代码提示词，开发团队可以：
- 提高开发效率
- 减少重复工作
- 确保代码质量
- 降低开发风险
- 保持项目一致性

记住，提示词是指导工具，不是硬性规定。在实际开发中，要根据具体情况灵活调整，确保最终交付高质量的代码和功能。
